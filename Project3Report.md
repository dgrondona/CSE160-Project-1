# CSE 160 Project 3: Reliable Transport

## Design

**Connection state.** Each node keeps a static table of 10 `socket_store_t` records, each with its own state, sequence positions, 128 byte send and receive buffers, retry count and deadline. A record is found by local port, remote address and remote port. A listener stays in LISTEN and spawns a new record in SYN_RCVD for each new SYN, so connections progress independently (`twoconn` runs two at once). States follow the textbook diagram: SYN_SENT, SYN_RCVD, ESTABLISHED, FIN_WAIT_1/2, CLOSING, TIME_WAIT, CLOSE_WAIT, LAST_ACK. We left out RST and simultaneous open. The full table is in `Project3Notes.md`.

**Packet format.** 8 byte header inside the IP payload: source and destination port (1 byte each), seq and ack (2 bytes each), advertised window (1), and one byte with SYN/ACK/FIN in the high 4 bits and data length in the low 4. A 28 byte payload minus the 8 byte IP header and 8 byte TCP header leaves 12 data bytes per segment. Addresses come from IP. Fields are big endian nx types, and a compile-time check keeps the struct exactly the IP payload size.

**Sequence numbers.** 16 bit, wraparound-safe compares, clock-based ISN (`getNow()/4`). SYN and FIN take one sequence number each. Buffers are indexed by `seq % 128`, which stays right across wraparound because 128 divides 65536.

**ACKs and retransmission.** ACKs are cumulative (next byte expected) and sent separately for every data segment and FIN, including ones that are dropped. A pure ACK is never ACKed. The receiver only accepts the next expected byte. On timeout the sender resends everything from the oldest unacked byte, in order (Go-Back-N). The RTO is a fixed 3 s, checked by one 250 ms tick against a per-record deadline. A valid ACK resets the retry count. After 6 retries the record is released and the app gets FAIL. ACKs outside what was sent are ignored.

**Windows.** The sender keeps up to 48 bytes (4 segments) outstanding, limited further by the peer's window relative to its cumulative ACK, and sends a short segment when only part of the window is open. The receiver advertises 128 minus unread bytes. `write()` only accepts what fits in the 128 byte send buffer next to unacked data. With a zero window the sender probes with 1 byte every RTO, and the probe's ACK carries the current window. When a read reopens the window to a full segment, the receiver also sends an update on its own.

**Cleanup.** The FIN goes out only once every byte before it is acked, and is accepted only in stream order. Unacked FINs are retransmitted. The active closer lingers in TIME_WAIT for 21 s (`RTO × 7`, longer than every FIN retry the peer could send) to ACK duplicate FINs, and `bind` won't reuse a port any record still holds. Records stuck in SYN_RCVD or SYN_SENT, or facing a dead peer, are released after the retry limit.

**Project 4.** The test app only uses the socket calls (`socket`, `bind`, `listen`, `accept`, `connect`, `write`, `read`, `close`), with split-phase `connectDone`, `remoteClosed` and `closeDone` events and polled `accept`. A chat or web app can use the same calls and the same multi-connection table.

## Discussion

**1. Fixed vs. varying initial sequence numbers.** A fixed ISN like 0 makes logs easy to read, but every instance of a tuple then uses the same sequence space. A segment delayed from an earlier connection could land inside the new connection's window and be taken as real data or a real ACK. We use a clock-based ISN, so a new instance starts somewhere else and old segments fall outside the window and get dropped. Two more guards: TIME_WAIT lingers longer than the peer's FIN retries, and `bind` refuses a port that a lingering record still holds. The cost is harder-to-read logs, plus a 16 bit ISN that wraps about every 4.4 minutes. That's far longer than a packet can live with a TTL of 15.

**2. How the advertised window changes.** It starts at 128. Each in-order segment shrinks it by its length, and each `read()` grows it by what was read. In `flow` the paused consumer lets it fall to 0. After resume, each 24 byte read raises it until the sender catches up. A useful buffer size, if the 128 limit were relaxed, is about the bandwidth-delay product: enough to cover a full round trip of data at the rate the path supports, plus slack for an app that reads in bursts. Much more than that just costs mote RAM, and our 1 byte window field caps it at 255.

**3. A data segment arrives twice because its ACK was lost.** By the time the duplicate arrives, the receiver's next expected byte is already past it, so the segment fails the in-order check and is dropped before it reaches the buffer. The receiver still sends its current cumulative ACK, which tells the sender everything up to that point arrived, so the sender moves on. In `acklast`, node 4 logs `DATA_RX dropped! ... expected` for the repeat, ACKs again, and the server still finishes with 0 mismatches.

**4. Why advertise new space after a read.** The sender only learns the window from ACKs, and ACKs are triggered by data. After a 0 window, the sender stops sending, so without an update the receiver would never send another ACK and both sides would wait forever. If the update is lost, our sender's zero-window probe covers it: a 1 byte segment every RTO, which the receiver drops if there's no room and always ACKs with the current window. In `flow` the first update is dropped on purpose, and the next probe's ACK reopens the window about a second later. Probes reset the retry count when ACKed, so a paused receiver is never mistaken for a dead one.

**5. Incomplete handshakes exhausting the table.** Every SYN from a new tuple takes a record in SYN_RCVD, and the table has only 10 records, shared with the node's own sockets. A half-open record is held until its SYN-ACK retries run out, about 21 s (7 × 3 s). Ten SYNs in that window that never complete would block all new connections and even local `socket()` calls. One improvement is a per-listener backlog limit on SYN_RCVD records, with a shorter SYN_RCVD timeout. Another is SYN cookies, so no state is kept until the final ACK proves the client is real.

**6. A peer that connects and goes idle.** With nothing outstanding, no timer runs, so an idle ESTABLISHED record lives forever. The `unreachable` run shows this: the client gives up after its retries, but the server's record stays open because the server had nothing to send. An idle timeout reclaims the record, but it also kills legitimate long-lived connections that are just quiet, like a chat session in Project 4. A middle ground is a keepalive: after a long idle period, send a probe the peer must ACK, and release only after the normal retry limit fails. A live peer costs one small exchange, and a dead one gets cleaned up.
